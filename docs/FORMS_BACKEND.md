# Client forms, admin console & PDF backend

This covers the client forms portal (`/forms`), the admin console (`/admin`), and the Supabase backend behind them.

## Setup (one-time)

1. **Environment variables.** Copy `.env.example` to `.env.local` and fill in all three values from
   *Supabase → Project Settings → API*. `SUPABASE_SERVICE_ROLE_KEY` is server-only: never prefix it
   with `NEXT_PUBLIC_` and never commit it. Add the same three variables to your hosting provider (e.g. Vercel).
2. **Database.** Run `supabase/migrations/20260929120000_forms_backend.sql`. Either paste it into
   *Supabase → SQL Editor* and run it, or use `supabase link` then `supabase db push`.
   It upgrades the existing `submissions` table in place, removes the old permissive policies, and is safe to re-run.
3. **Auth redirect URLs.** In *Authentication → URL Configuration*, set the Site URL to your live domain and
   add `https://<your-domain>/auth/callback` (plus `http://localhost:3000/auth/callback` for development)
   to the redirect allow-list. The sign-up confirmation and password-reset emails use this route.
4. **Create an admin.** Go to *Authentication → Users → Add user* (or sign up at `/forms/signup`), then run:
   ```sql
   update public.profiles set role = 'admin' where email = 'you@clear-debt.co.za';
   ```
   Admins sign in at `/admin/login`. There is no self-service way to become an admin.

## How it fits together

| Piece | Location |
|---|---|
| Form definitions (fields, rules, terms text, signature pads) | `src/lib/forms/definitions.ts` |
| Shared validation (browser + server) | `src/lib/forms/validation.ts` |
| Save / submit / PDF / status / delete logic | `src/lib/submissions/service.ts` |
| PDF renderer (pdf-lib) | `src/lib/pdf/generate.ts` |
| API routes | `src/app/api/**` |
| Client portal pages | `src/app/forms/**` |
| Admin console pages | `src/app/admin/**` |
| Session refresh + route protection | `src/middleware.ts`, `src/lib/auth.ts` |

To **add or change a field**, edit `definitions.ts`. The form, server validation, admin view and PDF all update from it.
Don't rename an existing field `name`: stored submissions use it as the key in `submissions.fields`.

### Data model

- `submissions`: one row per form. Searchable/sortable columns (`client_name`, `id_number`, `phone`, `email`,
  `status`, `form_type`, dates) plus a `fields` JSONB column holding the form-specific answers. `reference` is
  generated by the database (e.g. `CD-CT-260929-00042`). `pdf_path`, `pdf_generated_at` and `pdf_error` track the PDF.
- `submission_files`: signatures (and any future uploads), stored in the private `signatures` bucket.
- `submission_events`: audit trail recording who created, submitted, reviewed or regenerated what, including PDF failures.
- `profiles`: one per user, carrying `role` (`client` | `admin`).

### Security model

- Row-level security: clients can read only their own submissions, and admins can read everything.
- The browser never writes to the database or storage. API routes check the session and ownership
  (through the user's RLS-scoped client), validate the input server-side, and only then write with the service role.
- The `signatures` and `pdfs` buckets are private and have no storage policies. PDFs are streamed through
  `/api/submissions/:id/pdf` after an owner/admin check, so no storage URL is ever exposed.

### Workflows

- **Client:** Menu → Forms → sign up / sign in → fill in the form (save a draft any time) → Submit → the server validates,
  saves and generates the PDF → success page with View/Download PDF. If PDF generation fails, the submission is kept
  and the PDF is generated on first download.
- **Admin:** `/admin` dashboard (live statistics) → Submissions (search, filter, sort, paginate) → open a submission →
  review status and notes, view/download the PDF, regenerate it from the stored data, or delete it.
